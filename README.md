# Apparitor

Discord-бот доступов для серверов сообщества русской Википедии и Арбитражного комитета.
Проверяет вики-аккаунт участника (OAuth 2.0 через Мету, только идентификация) и выдаёт роли
по флагам в рувики. Хостится на Toolforge: https://apparitor.toolforge.org

## Команды
- `/login` — вход своей учёткой Викимедиа, привязка и роли.
- `/verify <имя>` + `/confirm` — запасной путь без OAuth: код в описании любой правки.
- `/status [имя]` — флаги участника рувики.
- `/sync` — пересчитать роли всем привязанным (нужно право Manage Roles).
- `/link @участник <имя>` — привязать вручную, когда ник никогда не совпадёт (Manage Roles; кто привязал — в журнале).
- `/audit` — сопоставить всех участников сервера с рувики, отчёт файлом (Manage Roles).
- `/optout-post` — опубликовать в канале ролей сообщение с 📭: выход из readme/announcements (Manage Roles).

## Фоновые функции (по серверу, в конфиге)
- `gate_watch` — раз в 5 минут бот спрашивает WikiAuthBot-ng (`/whois`, ключ сервера в `WIKIAUTHBOT_KEY_<id>`),
  нет ли у непроверенных участников связки с учёткой Викимедиа; нашлась — правило впуска сервера и роли
  (вхолостую — сводка в служебный канал). Новичков первых двух суток — каждый обход, остальных — раз в 6 часов.
- `starboard` — доска лучших сообщений (замена Starboard) в `board_channel_id`: при `board_threshold` звёздах ⭐ (звезду автора не
  считает, `board_self_star`) бот пишет строку «⭐ **N** | ссылка» (🌟 от 10, 💫 от 20) и пересылает сообщение штатным forward,
  без чтения текста. Источник открыт, если его видит роль `board_open_role` (по умолчанию «all») и он в одной из
  `board_categories` (пусто — любая); категория открытости не гарантирует. Каналы из `board_sources` берутся всегда
  (решение людей). Нет роли «all» на сервере — бот не работает и пишет об этом; личные ветки не берёт. Закрытое на
  открытую доску не попадает. Счётчик в строке обновляется. Нужны права просмотра и чтения истории источников.
- `import_links` — раз в сутки (и при старте) связки всех участников без связки в БД бота берутся из WikiAuthBot по `/whois`
  (method `wikiauthbot`, имя по номеру CentralAuth) и сохраняются в `links`: после ухода WikiAuthBot подтверждение
  не пропадёт. Уже связанных не трогает; пишет только в БД бота, ролей не меняет; итог — в служебный канал.
- `track_categories` — новый канал в этих категориях получает роль доступа (префикс + имя канала) и строку
  с реакцией 🇦…🇿 в сообщении бота в `roles_channel_id`; канал вне них или видимый без ролей — строка в служебный канал.
- `optout_channels` — реакция 📭 прячет эти каналы участнику (запрет на участника) и включает пересылку их новых
  сообщений в личку; короткий канал (до 30 сообщений, readme) присылается целиком. Сначала проверяется,
  что личка открыта.

## Функции Carl-bot (замена на сервере сообщества)
Включаются по одной в `[guild.<id>.features]`: `dry` — бот пишет в служебный канал, что сделал бы, и через
`PARITY_DELAY` секунд сверяет с тем, что Carl-bot сделал на самом деле («совпало» или «РАСХОЖДЕНИЕ»); `live` — действует сам;
нет ключа — выключено. Режим функции не зависит от `dry_run` сервера. Переключение — по одной функции: Carl выкл → live.
- `join_roles` — роли из `join_roles` («🆕 new user») через `join_delay` секунд после входа; Carl-bot выдаёт её через 240 с
  (журнал аудита), 0 = сразу. Вышедший за это время роли не получает.
- `welcome` — приветствие в `welcome_channel_id` (текст сообщения Carl дословно, `welcome_text`).
- `farewell` — прощание-embed с одним из `farewell_texts` в `farewell_channel_id`; 0 = никуда (в #welcome ник ушедшего
  увидели бы новички).
- `sticky_roles` — роли ушедшего возвращаются при повторном входе. Не возвращаются: роли с правами управления
  (администратор, управление ролями, каналами, сообщениями, баны, исключение и др.) и роли из `sticky_skip` (чёрный список
  Carl-bot) — их возвращает человек.
  Хранится `sticky_days` дней (по умолчанию 730).
- `reaction_roles` — роли по реакциям на сообщениях Carl-bot из `[guild.<id>.reaction_roles."<id сообщения>"]`
  (эмодзи → имя роли, режим Normal; кастомные эмодзи — по id). Белый список сообщения `[guild.<id>.reaction_require]`:
  роль получает только держатель одной из перечисленных ролей (подписки — только ✔). Для событий нужен просмотр канала
  с этими сообщениями.

## Что бот НЕ делает
- Не читает сообщения: Message Content Intent не запрашивается. Пересылка в личку — штатный forward Discord,
  текст боту для этого не нужен.
- Не хранит OAuth-токены: после чтения имени участника токен выбрасывается.
- Не хранит почту и другие данные профиля: только имя участника, Discord ID и глобальный id учётки.
- Для возврата ролей хранит id ролей ушедшего участника (`sticky_days` дней) и отпечаток последней сводки обхода
  по участнику (не текст).
- Логирует только действия и идентификаторы, без текста сообщений.

## Откуда флаги
Группы участника — из API рувики (`list=users`), глобальные (стюард и т.п.) — `meta=globaluserinfo`.
Статусы без технической группы — ПИ+, борцы с вандализмом, клерки, технические удаляющие, VRTS,
а также полный состав АК (в группе `arbcom` нет арбитров-админов) — из `MediaWiki:Gadget-markadmins.json`
(обновляет MBHbot раз в несколько дней), кэш 6 часов. Ключи карты ролей: `closer-plus`, `vandalfighter`,
`clerk`, `techdeleter`, `vrts`, `arbcom`. ПИ+ заменяет ПИ: при сопоставленной роли ПИ+ роль ПИ не выдаётся.

## Режимы
`dry_run = true` — бот ничего не меняет, а пишет в служебный канал, что сделал бы. Можно задать на сервер
(`dry_run` в секции `[guild.<id>]`), как и свои критерии впуска (`[guild.<id>.admit]`, `apat_suffices` — АПАТ впускает сразу).
Роли и критерии впуска — в `config.example.toml`.

## Развёртывание (Toolforge, тул `apparitor`)
Один процесс `web` из `Procfile`: Discord-клиент и HTTP на `$PORT`. Хранилище — ToolsDB
(база `<user>__apparitor`, создаётся один раз: `sql tools` → `create database <user>__apparitor character set utf8mb4`).
Секреты и конфиг — через envvars, в репо их нет:

    toolforge envvars create DISCORD_TOKEN …
    toolforge envvars create OAUTH_CLIENT_ID …
    toolforge envvars create OAUTH_CLIENT_SECRET …
    toolforge envvars create APPARITOR_CONFIG config.toolforge.toml
    toolforge build start https://github.com/ruwiki/apparitor
    toolforge webservice buildservice start
    curl https://apparitor.toolforge.org/healthz     # ok

Обновление: `toolforge build start …` и `toolforge webservice restart`. Логи: `toolforge webservice logs`.

## Структура кода
| модуль | что | зависимости |
|---|---|---|
| `models.py` | `UserInfo`, `Decision`, формат времени — типы между слоями | — |
| `config.py` | TOML → `Config`/`GuildCfg`/`Admit` | — |
| `mw.py` | клиент API MediaWiki (одна вики, бэкофф 429); сюда же ляжет запись для арбвики | aiohttp |
| `ruwiki.py` | рувики как источник флагов: группы, статусы из JSON гаджета, CentralAuth → `UserInfo` | mw |
| `rules.py` | впуск и роли: чистые функции | config, models |
| `match.py` | сопоставление по нику: кандидаты, выбор | models |
| `audit.py` | сборка отчёта /audit из строк | models |
| `store.py` | ToolsDB/sqlite: связки, ожидания, кандидаты, журнал | models, pymysql |
| `bot.py` | Discord-клиент, отчёты, применение решения | всё выше |
| `commands/` | slash-команды: `identity` (все), `admin` (Manage Roles) | bot |
| `web.py` | OAuth-колбэк, healthz | bot |
| `wikiauthbot.py` | клиент WikiAuthBot-ng `/whois` | aiohttp |
| `gate.py` | обход непроверенных: связка → правило → роли, сводка | bot, wikiauthbot |
| `rooms.py` | новые каналы, реакции, выход из каналов и пересылка в личку; роли по реакциям на сообщениях Carl | bot, store |
| `board.py` | доска лучших сообщений: подсчёт ⭐, строка счётчика и forward в канал доски | bot, store |
| `joins.py` | вход и выход: роли при входе, возврат ролей, приветствие и прощание, сверка с Carl-bot | bot, store |
| `wall.py` | скрипт (не часть бота): стена прав сервера — snapshot, plan, apply, rollback | config |

Новый источник (арбвики, Google Groups, WikiAuthBot) = свой модуль уровня `ruwiki.py`, который отдаёт
данные типами из `models.py`; правила и команды его не знают.

## Стена прав (скрипт `apparitor/wall.py`)
Цель: зашедший без проверки видит только новый `#welcome`, где новички и модераторы; `#readme`, `#announcements`,
`#server-hub` и старый `#welcome` видят проверенные (✔). Бот этого сам не делает — это отдельный разовый скрипт.

    python -m apparitor.wall snapshot --dir D --token-file ТОКЕН_ВИДЯЩИЙ_ВСЕ_КАНАЛЫ --read-token-file .env --read-bot
    python -m apparitor.wall plan     --dir D                      # печать: «было → стало» по каждому каналу и кто что видит
    python -m apparitor.wall apply    --dir D --token-file ТОКЕН   # без --yes — только печать; с --yes — исполнение и проверка
    python -m apparitor.wall rollback --dir D --token-file ТОКЕН   # без --yes — только печать

- Снимок и план читают; пишут только `apply --yes` и `rollback --yes`. Для записи нужен токен с Manage Channels, Manage Roles,
  Manage Guild и ролью выше Apparitor. `D` — рабочая папка вне репозитория (в снимке id участников).
- Правки минимальные: добавляются или убираются отдельные биты, а не заменяются все перекрытия канала — запреты на участников
  и роль «✔ read-only 🔇» остаются. Новый `#welcome` создаётся на основе прав старого, но без просмотра у «🆕 new user».
- `apply` заново читает сервер и сверяет отпечаток с `plan.json`; расходится — не пишет ничего. Каждая операция идёт в
  `changes.jsonl` сразу; на первой ошибке остановка. После — сверка записей с планом.
- `rollback` возвращает только записи, поставленные `apply`, и только если с тех пор их никто не менял (чужие правки
  не затираются). Новый `#welcome` не удаляется, а прячется.
- Системный канал сервера по умолчанию остаётся прежним (`--system-channel` переносит его в новый `#welcome`).
- Группы `--groups`: `wall` (каналы), `roles` (Apparitor в #roles), `position` (роль Apparitor, по умолчанию 49 — выше
  самой верхней реакционной роли), `board` (просмотр источников и запись в канал доски; не входит в умолчание).
  Боты, которым нужен просмотр закрываемых каналов, перечислены в `Spec.bot_view`; остальных `plan` печатает списком.

## Локальная отладка
`cp config.example.toml config.toml`, `.env` с теми же переменными, зависимости
`pip install --target vendor -r requirements.txt`, `./run.sh`. Хранилище задаётся в конфиге: `[db] kind = "sqlite"` локально, `"toolsdb"` на Toolforge.
